Syncy Care: The Complete Product Guide
Oct 20, 2026 · @Moses
What Syncy Care is
Syncy Care is a self-hosted MCP server, built for the Alexa+ track of the Amazon Developer Hackathon, that helps a hospitalized patient understand their own care without ever making a clinical decision. It turns the clinician-approved care plan into plain answers about what is happening, what changed, what comes next and what to ask, and it tells the care team where the patient is still confused.
The problem. A hospital stay produces a flood of information: many staff, tests, changing plans, medication swaps and a discharge sheet. Patients are tired and often cannot keep up. Hospitals are expected to communicate in ways patients understand, and poor understanding is linked to errors and worse outcomes. Most hospital software records whether information was given, not whether the patient understood it.
The thesis. Syncy keeps a persistent model of what the patient has been told, what changed in their care, what they understand, and what still needs a human to clarify. The AI explains. The clinician interprets.
Who it serves.
• Patients and families get answers at the bedside by voice, without waiting for someone to walk in.
• Nurses get fewer repeated questions such as "when is my test?".
• Doctors get better-prepared patients and a view of where communication broke down, not another AI diagnosis.
• The hospital gets a record of discharge teach-back.
What it is not. It is not a symptom checker, a diagnosis tool, a dosing tool, a discharge decision-maker or a medical device. It uses synthetic data only.
The patient experience
A patient asks in their own words and gets an answer labelled with where it came from: the care plan, general education, or "ask your care team". Each patient-specific answer also returns the source record it was built from, such as ServiceRequest/SR-02047.

The clinical boundary
On the simulator path, every request is classified in code before anything is answered. Over MCP, each tool carries its own policy, and the tool descriptions tell the agent to send any clinical-decision request to create_question_for_team. The boundary lives in code and tool design, not only in a prompt. Three levels decide what Syncy may do.

What always goes RED. Starting, stopping, skipping or changing medication; dosing; diagnosis and "what's wrong with me"; prognosis and survival; whether it is safe to leave or be discharged; whether a result is bad or normal or what a scan shows; and attempts to make Syncy act as a doctor or ignore its rules.
How the classifier works. src/core/safety.ts holds 15 RED patterns and 3 YELLOW patterns, checked in that order: RED wins, then YELLOW, otherwise GREEN. The fixed RED reply is: "That's a decision for your clinical team. I can't tell you to start, stop or change anything, or interpret what it means for you. I've added your question for your nurse so they can review it with you."
Defense in depth.
1. On the simulator path the rule-based classifier runs first; over MCP, the tool policies and descriptions do that job.
2. Tools return only approved facts with provenance; the model never reads the chart directly.
3. If Bedrock is configured, it only rewords text the tools already approved, and a Guardrail can be attached.
4. An output check rejects reworded text that looks like clinical advice (a dose in mg, "you probably have", "you should stop") and falls back to the approved original.
5. Every action is written to an audit log.
Hospital-defined warning signs. Syncy reads back the hospital's warning signs verbatim and never invents them.
Honest limit. The classifier is keyword-based, and the 38 test prompts were written by the same people as the rules. They are a baseline, not proof of safety. An independent set of adversarial prompts is still needed.
Architecture
Syncy Care is one Express server that exposes MCP and a simulator API over the same service layer.
Requests arrive by MCP or the simulator API. The simulator path runs the classifier first. Every tool reads synthetic data and returns approved facts with a policy and source record. Only simplify_text can call Bedrock, and it only rewords text that a tool already approved.
The 13 MCP tools
The server exposes 13 tools over MCP spec 2025-11-25 on Streamable HTTP (POST /mcp, stateless). Every result returns policy, source (care_plan, general_education or ask_care_team) and a source record. The model can only call these tools; it never reads the chart.

Other endpoints. GET /health reports the store and whether Bedrock is on. POST /api/ask runs the same classifier and tools from natural language for the simulator. GET /api/dashboard returns understanding state, the question queue and the audit log. POST /api/questions/:id/review marks a question reviewed. GET/DELETE /mcp return 405 because the server is stateless.
The core engines
Four small pieces of deterministic code carry the product. None of them depends on a model's medical judgment.
1. Change diff (diff.ts). Each patient has a yesterday snapshot and a today snapshot of plan items (medications, tests, plan entries), each with an id and status. The diff reports an item as new, as a status change (for example active → discontinued), or as removed, and tags it with its FHIR-style resource type (MedicationRequest, ServiceRequest, CarePlan). "What changed?" is therefore a computed answer, not an LLM recollection.
2. Understanding state. Each patient has five topics: plan, meds, tests, discharge and follow-up. Each is not_reviewed, explained, understood or needs_clarification. Explaining a topic moves it from not reviewed to explained, but never overwrites a stronger status that came from evidence such as a teach-back. The care-team dashboard reads this state to show where communication may have broken down. It is deliberately not a clinical risk score.
3. Teach-back (teachback.ts). For each discharge medication the care team has approved an instruction and a set of criteria, each a pattern the patient's answer must match. The patient's answer is checked against those criteria only, so no model opinion about medicine is involved.

Example: Jordan answers "I take one in the morning". The dose, frequency and food criteria are all missed, so the result is needs_clarification, the meds topic is flagged, and Syncy replies with the approved instruction and asks Jordan to confirm with the nurse. A full correct answer returns understood.
4. Question queue and audit trail. Anything RED, and any YELLOW question the chart cannot answer, becomes a pending question for the care team with the priority "Patient-requested review". Every tool call writes an audit event: time, patient, what was asked, tool, policy, source and result. Together they show a reviewer exactly what Syncy did and why.
Bedrock rewording (bedrock.ts). When BEDROCK_MODEL_ID is set, approved text can be reworded in plain language (a 5th-grade level for "simpler") with an optional Guardrail. The model is told to use only the given facts and add no advice. On any error, a guardrail intervention or advice-like output, the original approved text is returned.

Configuration (all optional). SYNCY_TABLE switches the store to DynamoDB. BEDROCK_MODEL_ID turns on rewording. BEDROCK_GUARDRAIL_ID and BEDROCK_GUARDRAIL_VERSION attach a Guardrail. PORT and ALLOWED_ORIGIN control the server.
What the 46 tests cover: 38 classifier cases (20 RED, 14 GREEN, 4 YELLOW); RED prompts blocked, queued and free of clinical advice; source records on patient-specific answers; one patient's data never appearing in another's answers; rejection of unknown patients; Maria's change diff; and three teach-back cases (wrong answer, correct answer, medication with no approved instruction).

Known gaps in the design
• The classifier is keyword-based and can miss paraphrases; a reworded dangerous question could be treated as GREEN.
• Data is hand-written JSON shaped like FHIR, not a real FHIR store.
• Maria's "what changed" returns five changes, while the original pitch said three.
• Family mode is a consent toggle in the simulator; real use needs proper authorization.
• The server has no authentication; production would use Cognito or hospital single sign-on.
• The in-memory store loses state on restart.
